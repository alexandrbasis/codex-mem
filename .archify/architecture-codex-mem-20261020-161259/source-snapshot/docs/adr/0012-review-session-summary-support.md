# Review material note and summary fields before storage

Session summaries remain concise prose. Mandatory support review and a separate contradiction check run before the processor writes notes and a summary atomically. The checks use the same selected execution profile as generation. They are bounded, fallible judgments.

## Why the contract changed

Shape validation and valid source IDs did not prevent a completion claim from repeating the user's request instead of describing the answer. The first review contract, `summary-support-v1`, accepted a false attribute while citing contradictory original evidence. Quote ownership did not establish support.

The second contract supplied complete field units and code-owned source spans. A live check still accepted a false whole-field claim. A general comparison prompt and an added source ledger also missed the contradiction. The current design separates candidate-blind interpretation of one original report from comparison with the candidate. Mandatory review of all original evidence remains in place.

## Original-source support

The `summary-support-v5` request supplies every complete nonempty summary field and material note field. Summary units retain their field names. Note units have indexed field paths. Text and typed arrays remain intact. The note catalog includes title, body, tags, observation type, subtitle, narrative, facts, concepts, files read and files modified. Four notes and seven summary fields produce at most 47 units.

Field purposes separate historical intent, investigated work, findings, completed outcomes, future work and other context. A requested attribute does not become a completed attribute. A bounded remainder of requested unfinished work is valid `next_steps` content without a new actor commitment. Added scope or deadlines still need evidence. Uncertainty about the supplied record does not assert universal absence. A progress checkpoint or disconnected stream does not establish final process status.

Observation categories follow the evidenced work or finding. The source does not need to name the category literally. `discovery` can describe a finding or evidence limit without completion. `bugfix` needs an actual correction. `decision` needs an accepted choice and rationale. `feature`, `refactor` and `change` need an observed change. Topic labels need topical fit. Any label that implies a factual status needs the same scoped support as prose.

The response contains flat comparison rows. Each row names its unit and states coverage, candidate meaning, evidence meaning, value comparison, attribution comparison, scope comparison and verdict. The verdict is `supported`, `unsupported`, `contradicted`, or `insufficient_context`. Every unit needs one to eight comparisons with consistent coverage. The whole response permits at most 64 rows. Incomplete coverage yields uncertainty. Bounds or missing units prevent acceptance. A supported topic cannot cover a contradictory attribute.

Code creates contiguous source spans of at most 1,200 characters, with stable IDs, offsets and exact text. Every disclosed source retains its full parent body, role, order and current/history group. Supported and contradicted rows need a known evidence span. Other verdicts can have no span. The decoder rejects unknown references, missing units, invalid shapes and exceeded bounds. Duplicate JSON keys and trailing data remain invalid in both native adapters.

For `title`, `investigated`, `learned`, `completed` and summary `notes`, each row also selects one to three spans owned by that exact candidate field. Its explicit report binding distinguishes `report_text`, `reported_content`, `other` and `unresolved`. Code supplies a catalog of original assistant reports. Report anchors must belong to that catalog and also appear in the row's evidence spans. Text properties are `language`, `organization` and `content`. Reported content permits `content` only. `other` and `unresolved` require empty report anchors and properties. An unresolved binding adds uncertainty. General source IDs and selection of the latest report do not establish this binding.

Historical `request`, future `next_steps` and all note units use `outside_outcome` with empty candidate spans, report anchors and properties. They still receive mandatory original-source support review. Source spans and report bindings establish ownership, not semantic truth. Historical derived records cannot override contradictory original evidence. The candidate cannot support itself. Mechanical coverage does not prove complete assertion extraction or correct interpretation.

The model-facing `summary-support-v5` row schema now expresses the existing unit-owner and binding-category constraints. Each outcome unit permits only its own candidate spans. Excluded units require `outside_outcome` with empty binding arrays. Report text and reported content use their existing distinct binding rules. Shared span catalogs use `$defs` and `$ref`. Wire fields, version and the authoritative local validator remain unchanged. Code checks duplicate references, citation subsets and complete unit coverage. Fallible model review assesses meaning and semantic support. Schema validity does not prove semantic support. This schema change has offline checks only. Live provider acceptance of the revised schema, including its maximum-size form, remains unverified.

Generation and review instructions preserve the supplied execution scope of an observed result. They do not invent local, regression, synthetic or production scope. Ambiguous candidate references can use context only within the same note or session-summary record. This does not narrow permitted original-source or historical context. Explicit claims cannot borrow attribution or weaker wording from another record. Evidence-limit wording must also support any implied event or success. Incidental descriptions of candidate formatting are omitted. The candidate remains non-evidence. These wording changes leave schemas, validators, limits and storage unchanged.

## Isolated current-report interpretation

After original support passes for a summary, `summary-source-v4` receives only the latest original assistant report in the current claimed batch. The model sees its verbatim bounded body between code-selected delimiters absent from that body. Source, session, turn, timestamp and current order stay in code-owned validation context. Surrounding instructions and output-schema text are not report evidence. The request contains no candidate, competing user request, history or derived memory. There is no historical fallback. Jev lifecycle-only envelopes do not count as original report text. Without a current original report, derived review records `not_assessed` and makes no derived model call. Note-only packets do not run this layer.

The model returns at most eight content propositions. Each retains statement, subject, time, modality and target. Modalities are `reported`, `observed_text`, `planned` and `unknown`. Targets are `report_text`, `reported_content` and `unresolved`. Code assigns IDs. The model also returns both mandatory text observations, `language` and `organization`, with their section scope. An observed slot needs a nonblank value and scope, with a null reason. An `unknown` or `not_applicable` slot needs a null value and a nonblank scope and reason.

Code retains all content propositions and both observation slots as at most ten source items, including planned, unknown and unavailable items. Only resolved available items can establish compatibility or conflict. The decoder rejects duplicate content propositions. Native schemas omit unsupported `uniqueItems`, while decoder duplicate checks remain active.

A later acknowledgement does not establish attributes of an earlier answer or external work. Report provenance identifies supplied text, without verifying its claims. `coverage=complete` does not mean all facts were extracted. Normalized interpretation explicitly records `coverage_is_exhaustive=False`. Partial coverage and unavailable observations remain visible. Code stores the SHA-256 of the exact report body with its identity. Interpretation reuse stays within this attempt and requires the retained-evidence fingerprint to remain current.

## Outcome consistency

The `summary-outcome-v5` request retains the complete nonempty `title`, `investigated`, `learned`, `completed` and summary `notes` fields with their purposes. Historical `request`, future `next_steps` and material note fields stay outside this layer. Original support remains mandatory for all of them.

For each support-bound claim anchored to the selected current report, code creates one relation with every source item from that report. No model-selected property or target filters these relations. The ceiling is 50 claim/item relations, enforced before dispatch. It is not a five-field by ten-item allowance. Multiple bound claims in one field can exceed the ceiling. The decoder requires each relation exactly once. Claims without a selected-report binding produce no relation. Such exclusions still depend on fallible semantic bindings from support review.

Code supplies the exact original report body once for all relations. Before dispatch, it joins the selected support record to interpretation by catalog ID, latest-current-report selection, current index, retained ID and provenance. It also requires the same body SHA-256 and complete ordered, contiguous owned spans with exact offsets and text. A foreign, missing or changed join fails before dispatch. The body must be nonempty and at most 100,000 characters. The whole prompt stays within 1,250,000 characters. There is no truncation or fallback to another report.

This body fixes a demonstrated loss of evidence. Earlier outcome input contained only a nonexhaustive extraction. Two supported language summaries became uncertain because that extraction omitted an occurrence count visible in the report. The full body supplies that context without changing candidate-blind source interpretation or discarding independent source items. Missing detail in the extraction is not proof of absence in the report. Reported external events remain reported.

Each row supplies `applicability`, `scope_relation` and `value`, with scope and value explanations. Code folds only these combinations:

| Applicability | Scope | Value | Code decision |
| --- | --- | --- | --- |
| `absent` | `not_compared` | `not_compared` | `unused` |
| `unresolved` | `unresolved` | `unresolved` | `uncertain` |
| `present` | `disjoint` | `not_compared` | `unused` |
| `present` | `unresolved` | `unresolved` | `uncertain` |
| `present`, available item | `aligned` | `compatible`, `incompatible`, or `unresolved` | `checked`, `contradicted`, or `uncertain` |
| `present`, unavailable item | `aligned` | `not_established` | `uncertain` |

Available items have `reported`, `observed_text` or `observed` availability and a resolved target. Planned, unknown, inapplicable and unresolved-target items cannot establish conflict. They remain required relations when a claim binds to the selected report. All other state combinations are invalid. When no relations exist, code skips the call and records `unused`. Unavailable items alone do not skip it.

Contradiction takes priority over uncertainty, then checked comparisons, then unused comparisons. Any contradiction or unresolved applicable comparison blocks storage. Scope includes subject, report region, time, attribution and modality. A later acknowledgement cannot contradict a property of an earlier report. Compatibility does not establish independent support. The model can still miss assertions, choose an incorrect report binding, or misread the body. This bounded check does not guarantee truth about external events.

## Correction, freshness and failure

Generation and all reviews share the immutable runtime, provider, exact model, reasoning level and monotonic deadline. The default remains 240 seconds. No new provider, key or model upgrade is required. Reviewers have no tools or correction callbacks. The optional Jev quality gate shares the existing single generation correction.

The first processed candidate whose reported validation reason is `missing_required_summary` can use the existing single correction. That reported reason does not establish that the initial candidate has no other errors. Structural and semantic correction share the same allowance, at most two generation turns and the original deadline. The corrected packet must pass all normal shape, source, support and applicable outcome checks. Malformed JSON, unknown source handles and other reported validation reasons do not gain this path. A rejected second candidate cannot trigger a third generation. No partial notes or summaries are written.

The returned receipt's `generation_correction` records `initial_reason_code=missing_required_summary` and the canonical candidate fingerprint. The durable generation `review_diagnostic` keeps its five keys: `version`, `candidate_fingerprint`, `evidence_fingerprint`, `status` and `invalid_subtype`. It records `invalid` and `structure`, without the exact initial reason. The fingerprint identifies the parsed, source-resolved canonical candidate, not raw output bytes. No raw candidate, source or reviewer telemetry channel is added.

A changed correction must pass shape, summary preservation, source membership and both applicable review stages again. Source interpretation is reused after freshness checks. An exact rejected summary or note cannot ask the model for another vote. The attempt keeps a rejection key over each rejected complete record, retained evidence, interpretation, immutable profile and contract versions. List position is not part of note identity. Reordering notes or editing another record cannot reset rejection. Only rejected records enter this cache. A corrected note does not inherit rejection from an unchanged supported summary. Shape and lease/source checks run before reuse. Operational failures are not cached, and the cache never crosses attempts, jobs or leases.

This rule conservatively preserves the first semantic rejection, including an erroneous rejection. It does not compare meanings or normalize text heuristically. A changed summary can use the remaining correction. A correction cannot remove a previously generated summary. Cached rejection adds no fabricated call or usage.

Store captures per-record fingerprints while it builds the exact current-source and historical views for a claim. These identities include all retained fields, structured metadata, source links and hydrated current tool I/O. Historical identities use complete retained records before excerpting. The processor compares selected captured identities with retained records before the initial fingerprint and before any generation call. Changed or deleted evidence fails with `summary_support_stale`. An unchanged bounded excerpt remains valid.

The processor passes the reviewed retained-evidence IDs, current-source IDs and aggregate fingerprint to Store. Store reads the same project-scoped records and current tool I/O inside its existing write transaction, before any output is inserted. Deletion or mutation after the final processor check blocks the whole packet. Unrelated projects and undisclosed records do not affect this guard. No model or processor callback runs inside the transaction.

Before Jev eligibility filtering, the processor checks the unfiltered captured identities. It checks again before cache reuse, before each live chunk after HTTP-slot acquisition, and after selection. Selected evidence is checked before generation and each native initial or correction turn. Both runtime adapters also check before native support, interpretation and outcome submissions. Optional Jev quality uses the same retained-identity check through its existing callback, including after its HTTP-slot wait. These checks preserve the original absolute deadlines.

A change visible at a guard denies that submission. A guard does not revoke a request already submitted, and a source can change after a guard. The final transaction fence prevents stale output writes. No database lock or transaction spans a model call. Earlier measured usage survives a later denial. Successful late review after lease expiry keeps the typed expiry outcome in both runtimes, retains owned call metrics and identifiers, and leaves ordinary retained-service recovery nonblocking. Actual malformed native records still fail as protocol errors. `generator_started` is marked after freshness allows generation handoff, not by native preparation alone. It does not prove provider acceptance.

Each review owns its metrics and worker identifiers in the call ledger. A failed review propagates its failure category without replacing the generation receipt. Measured review tokens add once; missing review counters keep the combined total unknown. The synthetic comparison recorder retains up to five ordered review executions in separate paths while generation remains single-use.

The separate cross-session `project_context` is a reference for generation and optional Jev quality. Quality receives it as `project_reference` with `evidence_role=reference_only` and cannot use it to replace missing support. It is excluded from mandatory support evidence and this content fingerprint. Existing freshness checks establish its record existence, not unchanged content.

Late negative or malformed reviews quarantine only the exact still-owned attempt. A replaced lease also preserves the `summary_support_stale` diagnostic without mutating its replacement. A replacement lease cannot be changed by an old reviewer. Changed sources, expired leases, malformed replies, failed calls and unresolved support prevent atomic storage. Raw work remains available. Rejection and uncertainty quarantine the failed batch while fresh work continues across service restart. Malformed, unavailable, stale and unknown operational failures retain the project-blocking policy.

Notes and summaries have separate relevance decisions. A useful session summary does not require a new durable note. Routine documentation, greetings and other low-value exchanges can still be skipped when neither output is justified. Earlier accepted substantive work still requires a summary. Native and injected generation retain the existing prohibition on summaries without a Stop. Every retained note receives mandatory original-source support review, with or without a summary. Useful supported tool-only notes remain allowed. The separate derived contradiction layer remains summary-specific and keeps its fifty-relation bound. Notes do not receive that extra layer.

## Accounting and compatibility

The additive `execution_calls` ledger contains generation, up to two original-support calls, one source interpretation and two outcome calls. At most two generation turns, two support calls, one source call and two outcome calls make seven native model calls. All use the selected profile. Unchanged rejection or no applicable report relations uses fewer calls. Generation can include its single correction and keeps cumulative checkpoints. Independent measured counters add once. A missing counter stays null, while measured per-call values remain available. Whole-attempt elapsed time counts nested review time once.

Operational diagnostics retain protocol version, status and candidate/evidence fingerprints. Allowed statuses are `pending`, `supported`, `rejected`, `uncertain`, `invalid`, `unavailable`, `interpreted`, `checked`, `unused` and `not_assessed`. Fixed invalid subtypes are `structure`, `unit_coverage`, `unknown_span`, `verdict`, `bounds`, `unknown_proposition`, and `duplicate_reference`. They contain no raw source or reviewer prose. Bounded correction feedback is untrusted data, never replacement evidence. Historical diagnostic versions remain readable. Historical attempts and stored note/summary shapes remain unchanged, including `verification=not_assessed`.

Tests inject generation and review separately through `process_pending` and `recover_failed_batch`. An injected generator without an explicit reviewer cannot start a live reviewer. Canned executable and local-provider tests establish protocol, lifecycle and accounting behavior only.

## Native Pi review schema

For `openai-codex` review calls only, Pi loads one package-owned schema helper explicitly while all other extension discovery remains disabled. The helper adds `text.format` and preserves the remaining payload. Its exact helper and schema hashes must match an application proof before acceptance. Missing, foreign, duplicate or tampered proof fails the review. The strict raw JSON decoder remains unchanged. Other providers and generation retain prompt-schema behavior.

These reviews use temporary SSE transport, disabled cache warming and zero provider retries. They keep the selected model, reasoning, provider and shared deadline. The helper makes no model calls and registers no tools, output handlers or continuations. Pi catches hook errors, so proof validation prevents acceptance but cannot retract an already-sent request. Receipts identify `bundled_schema_only` and the structured-output mode, hashes and status.

It established only that request. Later representative review controls passed on the exact Sol profiles described below. This small-schema probe alone does not establish that result or private acceptance.
