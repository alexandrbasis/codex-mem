# Codex Mem после 1.5.0 и сравнение с Claude Mem

Проверка выполнена 12 сентября 2026 года. Исходная версия Codex Mem: `700bae1`, 1.5.0. Новые изменения подготовлены как 1.6.0. Аудит установленной системы проводился до обновления плагина; приведённые ниже локальные тесты используют отдельные временные данные.

Claude Mem проверен по исходникам [13.24.23, commit ed57a511f5dbf84e75c9a785df818c43b66b5849](https://github.com/thedotmack/claude-mem/commit/ed57a511f5dbf84e75c9a785df818c43b66b5849). Это сравнение реализации и ограниченных тестовых сценариев. Сравнительного запуска Claude и Luna на одном наборе задач не было.

## Что показала работа установленной системы

Захват и обработка свежих событий продолжались. SQLite прошла проверку целостности. В снимке выбранного проекта все 357 доступных для индексации записей имели векторы, ошибок индексации не было. Три обнаруженных отказа `invalid_response` относились к 9 сентября. Их наличие само по себе не означало, что новая обработка остановилась.

Учёт токенов действительно отставал. Сборщик продвигал отметки чтения августовских файлов, а новые файлы текущего дня ещё не были прочитаны. Причина поддерживается и кодом: общий циклический обход тысяч файлов с ограничением на количество и байты не давал свежим файлам приоритета. Процесс был жив. Его раннее время запуска не доказывает работу на старом коде.

На отдельном вымышленном наборе из 1024 старых файлов и одного нового прежний сборщик учёл новое событие на 32-м проходе, новый на первом. После 40 проходов обе версии учли все 1025 событий без расхождений в суммах. Это проверка порядка обработки, а не подтверждение устранения отставания в установленной системе.

Диагностика также путала невозможность проверить PID в sandbox с остановкой сервиса. Исправленный отчёт показывает `unknown`, возраст последнего события учёта и доступность данных отдельно от здоровья базы.

## Что взято из Claude Mem

Компактный поиск перед чтением деталей. Заголовок выдачи Claude Mem содержит `ID`, `Time`, `Title`, `Tokens`; это видно в [реализации поиска](https://github.com/thedotmack/claude-mem/blob/ed57a511f5dbf84e75c9a785df818c43b66b5849/src/services/worker/SearchManager.ts#L690-L734). В Codex Mem CLI/MCP теперь не повторяют полные narrative, facts и поля summary в коротком ответе. Полные записи доступны через `memory_get`; `detail="full"` сохраняет прежний формат метаданных превью.

События вокруг результата поиска. Upstream `timeline` принимает `anchor`, `depth_before`, `depth_after`; это видно в [реализации окна](https://github.com/thedotmack/claude-mem/blob/ed57a511f5dbf84e75c9a785df818c43b66b5849/src/services/worker/SearchManager.ts#L746-L907). В Codex Mem добавлен точный `anchor_id` и ограниченное число соседних событий. Фильтры проекта и сессии применяются до отбора соседей. Отсутствующий ID возвращает пустое окно.

Это самостоятельная реализация принципов. Исходный код Claude Mem не копировался. Ранжирование поиска, полные записи и правила происхождения сведений сохранены.

На воспроизводимом наборе из восьми вымышленных наблюдений размер JSON поискового ответа уменьшился с 35 945 до 5 449 байт, на 84,8%. Порядок результатов сохранился, окно вокруг записи вернуло нужные пять событий, полные сведения остались доступны по ID. Это измерение размера ответа на конкретном наборе, а не общей экономии токенов аккаунта.

## Какие ошибки исправлены дополнительно

- Явный запрос повторить обработку больше не теряется, если приходит во время другого прохода.
- Проект остаётся в очереди, пока другой обработчик владеет действующим lease. Новый проход откладывается до безопасного момента.
- Автоматический повтор после таймаута привязан к точной задаче. Он не повторяет более старый отказ содержимого из карантина.
- Сборщик токенов получает отдельный приоритет для свежих источников и сохраняет ограниченную долю прохода для старого архива.
- Обновление управляемой установки проверяет владельца сервиса и его версию после корректного перезапуска. Незавершённая проверка обозначается как `restart_pending`, ошибка перезапуска как `restart_failed`. Копирование файлов не считается подтверждением обновления процесса.

## Что ещё имеет смысл взять

Следующий приоритет: учитывать расход самого наблюдателя. В Claude Mem отдельно сохраняются фактические входные и выходные токены, длительность и модель обработки; [код записи usage](https://github.com/thedotmack/claude-mem/blob/ed57a511f5dbf84e75c9a785df818c43b66b5849/src/services/worker/agents/ResponseProcessor.ts#L552-L615). Наш обработчик использует ephemeral-сессии, а сборщик читает сохранённые JSONL. Текущий журнал не подтверждает охват этих затрат. Сначала нужны реальные usage receipts наблюдателя с привязкой к задаче, затем расчёт расходов системы.

Второй кандидат: различать подтверждённое исчерпание лимита и другие ошибки провайдера. Upstream сохраняет [cooldown квоты](https://github.com/thedotmack/claude-mem/blob/ed57a511f5dbf84e75c9a785df818c43b66b5849/src/shared/quota-cooldown.ts#L1-L175). Для переноса сначала нужен проверенный классификатор ошибок app-server; общий `runner_failure` нельзя автоматически считать временным.

Отдельные механизмы уже есть у обеих систем. Публичный путь поиска Claude Mem делает [FTS fallback](https://github.com/thedotmack/claude-mem/blob/ed57a511f5dbf84e75c9a785df818c43b66b5849/src/services/worker/SearchManager.ts#L547-L627), и у нас есть явный lexical fallback. Ограничение контекста целыми фрагментами у нас также уже реализовано. Переносить их повторно оснований нет.

Показатель upstream `discovery_tokens - read_tokens` описывает его [оценку сокращения чтения](https://github.com/thedotmack/claude-mem/blob/ed57a511f5dbf84e75c9a785df818c43b66b5849/src/services/context/TokenCalculator.ts#L6-L35). Он не доказывает чистую экономию с учётом работы компрессора. Поэтому здесь приведены измеренные байты и сохранена граница неизвестного расхода.

## Проверка изменений

Базовый набор 1.5.0 прошёл 294 теста. Два свежих запуска Luna/medium на временных вымышленных проектах сохранили причину проверенного исправления и не превратили противоречивую проверку в сообщение об успехе. Исходные свидетельства и ссылки на них сохранились. Это ограниченные сценарии, а не статистическая оценка качества модели.

Итоговый набор 1.6.0 прошёл все 347 тестов. Сценарий с противоречивой проверкой повторно прошёл через финальный процессор. Отдельная проверка с настоящим временным сервисом подтвердила смену владельца и версии при обновлении, единственность работающего процесса и сохранность базы, конфигурации и отложенной очереди.

Итоговые проверки рабочей версии и команды воспроизведения приведены в [VERIFICATION.md](VERIFICATION.md). Проверка hook/MCP использует временную базу; официальный JSON Schema hooks в этом проходе не валидировался. Локальные тесты не подтверждают обновление установленного плагина, desktop-каталога или пользовательской базы.
