# Preserve legacy identity in the shared host contract

The shared host contract retains existing Codex session IDs and recognizes legacy source names. Other host and branch sessions use a separate namespace. The same source classifier serves Python validation and SQLite selection, so adding a host does not require rewriting history. During capture, the store can recognize a legacy dedupe key as an alias in the existing transaction. This keeps source IDs and completed processing state stable across an upgrade. New delivery identity uses host and event identifiers, never text alone. Adapters retain response formatting and service wake requests. The shared core owns capture policy, provenance, and bounded untrusted context.

See [the host contract](../HOSTS.md) and [host/runtime separation](0010-separate-host-and-background-execution.md).

Identified deliveries now claim a body-free SQLite receipt before the shared capture operation changes privacy state. Replaying old public or private input cannot rewind a newer gate at this boundary. The receipt keeps only a scoped hash and outcome. It survives source deletion to prevent resurrection. A claim without a final receipt remains an explicit unknown outcome and is not replayed. This favors privacy over capture completeness after interruption. Source commits and background processing retain their existing transactions. Native Codex public transitions also use this boundary. Private hooks retain the immediate pre-SQLite marker and then create a body-free native-identity receipt. A repeated completed private action skips that marker. The receipt establishes only the privacy action, not source capture. A crash between marker and receipt can conservatively re-mark an uncertain private event. No SQLite wait precedes protection, and private bodies never enter these receipts.

Pi persists a branch activation marker in native custom entries. A successful tree navigation creates a new activation. Resume and reload restore the current marker. Forks use the new native session identity and do not recapture copied entries. Compaction retains activation and settlement state. Each activation requires a newly observed user before assistant/tool capture, because copied history cannot establish the current privacy state. Shared ancestry does not establish episode identity or authorize consolidation. See [Pi lifecycle behavior](../PI_HOST.md).
