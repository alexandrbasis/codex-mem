## 2. Как включим только для этого проекта

Недостающие папки размещаем в `.agents/skills/` этого репозитория. Это штатное расположение проектных скиллов Codex: “Put repo skills in .agents/skills when the workflow applies to that project”. [Официальная документация](https://learn.chatgpt.com/docs/customization/overview#skills).

Копируем каждую папку полностью: `SKILL.md`, `agents/openai.yaml`, справочники, шаблоны и скрипты. В частности, сохраняем форматы glossary/ADR, инструкции triage, шаблоны setup, `PHASE-BOUNDARIES.md` и сведения об авторстве `pr`.

Установка использует штатный `skill-installer` с параметрами `--repo mattpocock/skills`, `--ref` с закреплённым SHA и `--dest` с абсолютным путём проектной `.agents/skills/`. Перед установкой повторно определяем отсутствующие имена. Существующие папки установщик не перезаписывает.

Полный плагин автора не устанавливаем. Он повторил бы глобальные скиллы и добавил весь productivity-набор. Не запускаем авторский `link-skills.sh`, поскольку он меняет глобальные каталоги. Не используем отключённый APPMS как источник одноимённых скиллов: его варианты имеют другие зависимости.

В `docs/agents/skill-lock.json` фиксируем источник, SHA, список локальных файлов и их SHA-256, глобальные зависимости и проектные правки. Лицензию MIT сохраняем в `docs/agents/licenses/mattpocock-skills.txt`; авторские сведения внутри папок остаются на месте.

На этом компьютере глобальные зависимости разрешаются по установленным папкам. На другом компьютере проверка должна обнаружить их отсутствие. При переносе выполните настройку заново: выберите существующий глобальный источник или локальную установку для каждой зависимости, обновите пути и области в lock-файле и проверяющем скрипте. Записи включения создайте с путями нового компьютера. Текущая проверка закрепляет согласованное разделение 14 локальных и восьми глобальных скиллов; автоматического переноса нет.

Авторские скиллы для разработки не включаем в дистрибутив Codex Mem для конечных пользователей. При настройке проверим список файлов упаковки.

## 3. Совместимость с установленными версиями и Codex

По правке пользователя в Roughdraft восемь глобальных скиллов обновлены до закреплённого commit автора. Старые файлы и конфигурация сохранены в резервной копии. Остальные 14 скиллов установлены только в проект. Для всех 22 скиллов добавлены точные записи `enabled = true` в пользовательском `~/.codex/config.toml`, с сохранением прежних записей и настроек.

Проверка Codex `0.163.0` уточнила первоначальный способ подключения. Массив `skills.config` проекта заменяет пользовательский массив целиком. Поэтому проектный `.codex/config.toml` не создан. Пользовательские записи включения выбирают уже обнаруженные пути и не расширяют поиск скиллов. Runtime подтвердил область `repo` у 14 локальных скиллов и их отсутствие в другом каталоге. В каталоге Codex их имена имеют префикс `codex-mem:`, восемь глобальных имён идут без префикса.

| Расхождение | Проектное решение |
| --- | --- |
| Старые глобальные версии ссылаются на `CONTEXT.md` | Обновляем авторские файлы. Все скиллы используют единый `GLOSSARY.md`, без проектного переопределения. |
| Глобальный `tdd` отстаёт от upstream | Обновляем скилл целиком, включая актуальные правила границ тестирования. Согласованные в спецификации границы повторно не согласовываем. |
| Глобальная диагностика отстаёт от upstream | Обновляем скилл целиком, включая проверку искусственно вызванного падения на исходном коде. |
| `wizard/template.sh` старее upstream | Обновляем шаблон внутри существующего глобального `wizard`. Дополнительный проектный шаблон не создаём. |
| Upstream требует “Call the Skill tool”, которого нет среди инструментов этой сессии | Загружаем соответствующий `SKILL.md` доступным инструментом чтения. Общие скиллы разрешаем через реестр, ссылки на ресурсы сохраняем относительно их папки. |
| `code-review` сравнивает `<base>...HEAD`, а `implement` вызывает review до коммита | Адаптируем локальный `code-review` для явно выбранного режима: ветка, staged или рабочие изменения. Учитываем новые файлы и фиксируем состав изменений текущей задачи. |
| `ask-matt` описывает команды других сред и остальные productivity-скиллы | Отделяем установленный состав от дополнительных рекомендаций. `/clear` и `/compact` не считаем инструментами агента; продолжаем работу средствами текущей среды. |

Новый шаблон `wizard` отличается обработкой кавычек и значений `.env`, правами файлов и поведением при конце ввода. Его проверим отдельно на временных файлах. Секреты пользователь вводит самостоятельно.

В `agents/openai.yaml` сохраняем авторские режимы запуска. Одиннадцать engineering-скиллов доступны только по явному запросу пользователя. Их отсутствие в списке для автоматического выбора не означает отсутствия на диске. Например, глобальный `improve-codebase-architecture` существует, но не показан в текущем каталоге автоматически выбираемых скиллов.

Глобальные Markdown и `agents/openai.yaml` обновляем согласованно. `enabled = true` означает доступность скилла, а `allow_implicit_invocation = false` сохраняет его запуск по запросу пользователя. [Правила автора](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/.agents/invocation.md).

## 4. Правила письма, кода и документы проекта

У автора нет универсального файла coding styles, который можно перенести в Python-проект. В `retro` он пишет: “Reserve `CODING_STANDARDS.md` for genuine judgement calls”. Поэтому создаём собственные правила оценки кода, опираясь на Codex Mem. Требования, которые уже проверяет CI, не переписываем как ручной чек-лист. [Источник](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/retro/SKILL.md).

| Файл | Содержание |
| --- | --- |
| `CODING_STANDARDS.md` | Правила для review: границы Python-модулей, совместимость интерфейсов и хранилища, изоляция проектов, идемпотентность повторной обработки, происхождение утверждений, независимость тестовых ожиданий. Каждое правило связано с текущими источниками проекта. |
| `docs/agents/engineering-skills.md` | Маршруты работы, глобальные зависимости, совместимость, режимы review и правила обновления комплекта. |
| `docs/agents/issue-tracker.md` | Конкретный трекер, формат спецификаций и задач, зависимости и порядок завершения работы. |
| `docs/agents/triage-labels.md` | Соответствие пяти авторских ролей существующим меткам трекера. |
| `docs/agents/domain.md` | Один словарь `GLOSSARY.md`, решения в `docs/adr/`, связь с существующей архитектурой. |

Для writing style используем уже установленные `unslop`, `simple-english` и `writing-for-agents`. В проектном руководстве добавляем только распределение ответственности: первые два управляют ясностью текста, третий управляет структурой инструкций агенту. Сохраняем язык пользователя и существующие правила Roughdraft/human-review.

Авторский `.agents/writing-docs.md` описывает публикацию страниц его сайта. Из него полезны ясное назначение, условия выбора и наблюдаемый результат. Целиком переносить требования его сайта, словаря и структуры публикации в Codex Mem не нужно. Beta-скиллы `writing-beats`, `writing-shape`, `writing-fragments` посвящены написанию статей и в этот комплект не входят.

Технические проверки берём из текущих `pyproject.toml`, `.github/workflows/test.yml` и `docs/VERIFICATION.md`. Сейчас CI выполняет `unittest`, `scripts/acceptance.py` и `scripts/package.py` на Python 3.10, 3.13 и 3.14 для Linux и macOS. Настроенного typecheck или formatter в `pyproject.toml` нет. Не объявляем такие команды существующими и не добавляем TypeScript-инструменты из upstream.

Словарь и ADR создаём по мере появления проверенных терминов и принятых решений. Авторский `domain-modeling` прямо требует: “Create files lazily”. Пустые файлы и выдуманные решения не нужны. Текущая Archify-схема остаётся источником архитектурной структуры. [Источник](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/domain-modeling/SKILL.md).

## 5. Предлагаемая настройка трекера

Выбран GitHub Issues репозитория `alexandrbasis/codex-mem`. Пользователь подтвердил этот вариант 20 октября 2026 года. Репозиторий указан в `origin` и `pyproject.toml`.

Ниже проектные значения трёх файлов настройки. Файл трекера создаём из полного [авторского GitHub-шаблона](https://github.com/mattpocock/skills/blob/5beb35b040e3de97e54fa9e386d7e42d15c295c2/skills/engineering/setup-matt-pocock-skills/issue-tracker-github.md). Сохраняем его операции создания, чтения, связей и управления состояниями, затем применяем приведённые настройки.

`docs/agents/issue-tracker.md`:

```markdown

# Issue tracker

Спецификации и задачи находятся в GitHub Issues: alexandrbasis/codex-mem.
Перед изменением задачи прочитай её текущее состояние.
Для многострочных описаний используй файл и --body-file.
Связывай задачи со спецификацией и задавай зависимости средствами трекера.
Если нативная операция недоступна, фиксируй явную ссылку в описании задачи.
Закрывай задачу после подтверждения результата. При закрытии через PR используй
ссылку Closes и сохраняй задачу открытой до слияния.
PRs as a request surface: no.
```

В итоговом файле явно задаём операции для `wayfinder` и `implement-spec`:

| Операция | Представление и правило |
| --- | --- |
| Map и child | Карта решений является отдельной issue с меткой `wayfinder:map`. Дочерние задачи связаны через sub-issues; запасной вариант: список задач в карте и `Part of #N` у ребёнка. |
| Blocking | Нативная зависимость между issue. Для API используем database ID, не видимый номер `#N`. Запасной вариант: `Blocked by: #N` с чтением текущего состояния каждой зависимости. |
| Frontier | Открытые дочерние задачи без незакрытых блокеров и без исполнителя. Порядок берём из карты. Для задач с кодом зависимость считается готовой после попадания результата в интеграционную ветку. |
| Claim | Назначаем исполнителя до начала работы; повторно читаем задачу, чтобы заметить параллельное назначение. |
| Resolve | Исследовательский вопрос закрываем после записи ответа и ссылки в карте. Задачу с кодом связываем с PR через `Closes`; она закрывается при слиянии. |
| Integration branch | `implement-spec` собирает задачи на одной ветке. Завершённая работа агента и слитая ветка различаются; статус готовности к review не означает слияние. |

Версию CLI проверяем до использования команд шаблона. Сейчас установлен `gh 2.100.0`; доступность нативных операций на выбранном репозитории ещё не проверена.

## 7. Как будем работать после настройки

| Ситуация | Маршрут |
| --- | --- |
| Требования ещё неясны | По запросу пользователя `grill-with-docs`; внутри него `grilling` и `domain-modeling`. При необходимости исследование или прототип. |
| Небольшая задача уже понятна | По запросу пользователя `implement`, затем нужные циклы `tdd` и проверка `code-review`. |
| Работа займёт несколько сессий | `to-spec`, затем `to-tickets`. После согласования задач: `implement` по одной задаче либо `implement-spec` для параллельной работы. |
| Ошибка воспроизводится неочевидно | `diagnosing-bugs`, исправление и регрессионная проверка. |
| Нужно улучшить процесс или архитектуру | По запросу пользователя `retro` либо `improve-codebase-architecture`. |

Это набор доступных этапов. AGENTS.md не заставляет каждый небольшой запрос проходить интервью, спецификацию и разбиение на задачи.

У автора отдельные команды совершают действия: `to-spec` публикует спецификацию, `implement` создаёт коммит, `implement-spec` работает с ветками и задачами, `wayfinder` может отправлять исследовательскую ветку на сервер. Установка файлов сама по себе эти действия не запускает. При использовании учитываем исходный запрос пользователя и уже данную авторизацию; не запрашиваем её повторно.

При текущей настройке есть много незакоммиченных изменений Codex Mem. Они не становятся частью установки скиллов или её коммита. Ветки и worktree для будущего `implement-spec` создаются от явно выбранной интеграционной ветки; изменения других задач сохраняются.

## 8. Порядок внедрения и критерии готовности

1. Повторить проверку глобальных зависимостей. Сохранить резервные копии и обновить восемь глобальных скиллов до актуального commit. Завершено, когда авторские файлы совпадают с upstream, а у каждого имени один источник.

2. Установить 14 недостающих engineering-скиллов из закреплённого commit. Сохранить лицензию, метаданные и все ресурсы. `handoff` добавляется только при выборе этого дополнения.

3. Создать файлы настройки, правила работы в Codex, `CODING_STANDARDS.md` и дополнить AGENTS.md. Добавить записи включения всех 22 скиллов в пользовательский `~/.codex/config.toml`, сохранив остальные настройки и проектную область обнаружения. Для GitHub проверить права чтения и текущие метки; затем создать только недостающие согласованные метки.

4. Добавить `scripts/check_engineering_skills.py`. Он проверяет файлы, обязательные зависимости, имена, режимы вызова, хеши, включение и отсутствие повторных установок. Ссылки документов проверены отдельно. Проверка выполняется без записи.

5. Проверить обнаружение через Codex app-server `skills/list` и включение через `config/read`. Сопоставить пути, имена и области всех 22 скиллов. Проверить отсутствие локальных скиллов в другом каталоге. Временные Git- и `.env`-фикстуры проверяют команды review для staged, unstaged и новых файлов, а также шаблон `wizard`. Полный процесс с моделью и реальные записи подзадач/зависимостей не запускались как тест.


Приёмка установки требует наблюдаемого результата. Наличие папок не заменяет проверку обнаружения скиллов. Проверку, которая требует следующего хода или ещё не выполнена, отмечаем отдельно.

Полный тестовый набор продукта не нужен для одних инструкций. Если настройка затронет упаковку, CI или исполняемый код, запускаем относящиеся к изменению проверки. Проверки шаблонов используют временные данные; реальные задачи и публикации не создаются как тест.

Дальнейшее обновление выполняем по новому закреплённому commit: сначала diff и проверка зависимостей, затем перенос с сохранением проектных правок. Изменившийся глобальный скилл отображается как drift, а не молча заменяется локальной копией.

Обязательный объём: 14 новых проектных скиллов, восемь обновлённых глобальных скиллов, записи включения с сохранением проектной области и проектные документы. Существующие три Graphical-скилла сохраняются. Дополнительный `handoff`, если он выбран, увеличивает число новых папок до 15.
